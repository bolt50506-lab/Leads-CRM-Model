# Render deployment quick guide

## Architecture
One Render Python web service serves the existing frontend and FastAPI API. One Render managed PostgreSQL database stores shared users, assignments, leads, stages, tags, and activity data. Agents use separate credentials; backend authorization filters their data.

## Deploy steps
1. Put this folder in a private GitHub repo and push the code.
2. Render Dashboard → New → Blueprint → connect repo → apply `render.yaml`.
3. Use the paid plan settings in the Blueprint; the database free tier is not suitable for live company records because free databases expire.
4. Set the requested `ADMIN_EMAIL` and `ADMIN_PASSWORD` secret values during setup. `JWT_SECRET` is generated by the Blueprint.
5. Deploy and wait for `/api/health` to return `200`.
6. Open the service URL, log in as admin, create each real agent and assign leads.

## Keep the data safe
The production `DATABASE_URL` is Render Postgres, not a local file in the container. Never delete the Render database when redeploying. Imports do not delete unrelated leads. Admin-initiated deletes are separate actions and should be governed by the company's retention policy. Configure recurring logical exports and test a restore before importing production leads. Keep secrets and customer data out of Git.

## Update workflow
Push reviewed changes to the connected Git branch; Render builds and deploys the service. Database migrations should be reviewed and run as a controlled deployment step before schema-changing code is released. Back up before schema changes or large imports.
